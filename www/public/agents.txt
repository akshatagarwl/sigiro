# Sigiro — Agent Data Guide
#
# Read this file, then query the data with the sigiro CLI or HTTP API.
# All observability data lives in DuckDB tables (one per signal type).
# No separate stores, no PromQL, no LogQL — just SQL.

## What This Is

A per-signal observability store backed by DuckDB. Metrics, traces, and logs
are stored in separate tables optimized for their schema. You query with SQL
via the sigiro CLI or HTTP API.

## Schema

### sigiro_spans (traces)
| column | type | meaning |
|---|---|---|
| timestamp | TIMESTAMP | span start time |
| end_timestamp | BIGINT | span end (nanoseconds) |
| duration | BIGINT | span duration (nanoseconds) |
| trace_id | VARCHAR | distributed trace ID (hex) |
| span_id | VARCHAR | span ID within trace (hex) |
| parent_span_id | VARCHAR | parent span ID for call trees |
| service_name | VARCHAR | service name, primary filter |
| span_name | VARCHAR | operation name (e.g. POST /checkout) |
| span_kind | INTEGER | 0=unspecified, 1=internal, 2=server, 3=client, 4=producer, 5=consumer |
| status_code | INTEGER | 0=unset, 1=ok, 2=error |
| status_message | VARCHAR | error message if status_code=2 |
| resource_attributes | VARCHAR | JSON resource attributes |
| span_attributes | VARCHAR | JSON span attributes |
| events_json | VARCHAR | JSON span events |
| links_json | VARCHAR | JSON span links |

### sigiro_logs
| column | type | meaning |
|---|---|---|
| timestamp | TIMESTAMP | log timestamp |
| trace_id | VARCHAR | trace ID for correlation |
| span_id | VARCHAR | span ID for correlation |
| service_name | VARCHAR | service name |
| severity_number | INTEGER | OTel severity (1-24) |
| severity_text | VARCHAR | INFO, WARN, ERROR, etc. |
| body | VARCHAR | log message text |
| resource_attributes | VARCHAR | JSON resource attributes |
| log_attributes | VARCHAR | JSON log attributes |

### sigiro_metrics_gauge
| column | type | meaning |
|---|---|---|
| timestamp | TIMESTAMP | metric timestamp |
| metric_name | VARCHAR | metric name (e.g. process.runtime.go.mem.heap_alloc) |
| value | DOUBLE | gauge value |
| service_name | VARCHAR | service name |
| metric_attributes | VARCHAR | JSON metric attributes |

### sigiro_metrics_sum / sigiro_metrics_histogram / sigiro_metrics_exp_histogram
Same pattern — see schema.rs for full column lists.

## CLI Usage

```bash
# Start the server (gRPC :4317, OTLP HTTP :4318, query HTTP :9999)
sigiro serve

# Show services, row counts, DB file size
sigiro status

# Raw SQL query
sigiro query "SELECT count(*) FROM sigiro_spans WHERE service_name='checkout'"

# Investigate one or more services (structured JSON: metrics + spans + logs + linked traces)
sigiro investigate checkout
sigiro investigate checkout --from 1711000000 --to 1711001000

# Investigate multiple services at once (incident topology)
sigiro investigate checkout,payments,inventory

# Pipe investigation to an LLM
sigiro investigate checkout | llm "what's the root cause?"
```

## HTTP API

```bash
# Health check
curl http://localhost:9999/health

# Raw SQL query
curl -X POST http://localhost:9999/query -d "SELECT count(*) FROM sigiro_spans"

# Investigate one service
curl -X POST http://localhost:9999/investigate \
  -H 'Content-Type: application/json' \
  -d '{"service":"checkout"}'

# Multiple services in one call (max 10)
curl -X POST http://localhost:9999/investigate \
  -H 'Content-Type: application/json' \
  -d '{"services":["checkout","payments","inventory"]}'

# Custom time window (microsecond timestamps)
curl -X POST http://localhost:9999/investigate \
  -H 'Content-Type: application/json' \
  -d '{"service":"checkout","from_ts":1711000000000000,"to_ts":1711001000000000}'
```

## Investigation Playbook

Given: a service name and an approximate time of incident.
Goal: determine root cause.

### Quick start

```bash
sigiro investigate checkout
```

Returns an InvestigationBlock JSON with:
- **metrics**: 1-minute bucketed time series (p95, avg, count)
- **spans**: top 50 by error status + duration
- **span_trees**: parent_span_id → child span_ids mapping
- **logs**: template-deduplicated (body + severity grouped, with count)
- **linked_traces**: cross-service spans for error trace_ids (cap 5)

### Manual drill-down with raw SQL

#### Metrics — bucketed time series
```sql
SELECT time_bucket(INTERVAL '1 minute', timestamp) AS bucket,
       metric_name, approx_quantile(value, 0.95) AS p95, avg(value), count(*)
FROM sigiro_metrics_gauge
WHERE service_name='checkout'
GROUP BY bucket, metric_name
ORDER BY bucket, metric_name
```

#### Spans — errors and slow operations
```sql
SELECT trace_id, span_id, span_name, duration, status_code
FROM sigiro_spans
WHERE service_name='checkout' AND status_code = 2
ORDER BY duration DESC
LIMIT 50
```

#### Logs — two-pass investigation (saves tokens, reduces context poisoning)

If the service has many logs (hundreds+), use a two-pass approach:

**Pass 1 — Templates (cheap, high signal):**
Get deduplicated log templates with counts. This compresses thousands of lines
into a handful of patterns. Look for rare/new templates or error severity.
```sql
SELECT regexp_replace(body, '[0-9a-f]{8,}|[0-9]+\.[0-9]+\.[0-9]+\.[0-9]+|[0-9]+', '{id}', 'g') AS template,
       severity_text, count(*) AS n,
       min(timestamp) AS first_seen, max(timestamp) AS last_seen
FROM sigiro_logs
WHERE service_name='checkout'
GROUP BY template, severity_text
ORDER BY n DESC
LIMIT 30
```

**Pass 2 — Drill into suspicious template (targeted, full detail):**
Once you identify a suspicious template (rare occurrence, ERROR severity, or
new pattern), fetch the raw logs matching it to get exact values.
```sql
SELECT timestamp, body, severity_text, trace_id, span_id, log_attributes
FROM sigiro_logs
WHERE service_name='checkout'
  AND body LIKE '%connection%refused%'  -- match the suspicious template
ORDER BY timestamp DESC
LIMIT 20
```

**When to skip two-pass:** If there are <100 logs, just read them directly:
```sql
SELECT body, severity_text, count(*) AS n,
       min(timestamp) AS first_seen, max(timestamp) AS last_seen
FROM sigiro_logs
WHERE service_name='checkout'
GROUP BY body, severity_text
ORDER BY n DESC
LIMIT 30
```

#### Follow cross-service traces
```sql
SELECT trace_id, service_name, span_name, span_id, parent_span_id,
       duration, status_code
FROM sigiro_spans
WHERE trace_id IN ('abc123...', 'def456...')
ORDER BY trace_id, timestamp
```

## Platform Data Correlation

Sigiro stores app-level telemetry (traces, logs, metrics). It does NOT store
platform-level data (deploys, machine events, web vitals, infra metrics).
During investigations, YOU are the glue — fetch platform data and correlate
timestamps with sigiro's InvestigationBlock.

### Investigation workflow

1. sigiro investigate <service>  → get traces, logs, anomalies, span trees
2. Query the platform API for the same time window → deploys, events, metrics
3. Correlate: "deploy v1.2.3 at 14:32 → error spike in sigiro at 14:33"

### Vercel

Data to fetch (via Vercel REST API, needs VERCEL_TOKEN):
- Recent deployments: GET /v6/deployments?projectId=<id>&limit=10
  → deployment times, commit SHAs, build status
- Web Vitals: GET /v1/web-vitals?projectId=<id>
  → LCP, FID, CLS scores (Vercel Speed Insights)
- Serverless function logs: GET /v2/deployments/<id>/events
  → cold starts, timeouts, errors
- Environment: check VERCEL_REGION, VERCEL_URL env vars in spans

Correlate: deployment timestamp vs error spike in sigiro_spans.
Correlate: web vitals degradation vs slow spans (high p95 duration).

### Fly.io

Data to fetch (via Fly Machines API, needs FLY_API_TOKEN):
- Machine events: GET /v1/apps/<app>/machines/<id>/events
  → start, stop, exit (with exit code + signal), OOM kills
- Machine state: GET /v1/apps/<app>/machines
  → running/stopped/created, region, image ref
- Prometheus metrics: GET https://api.fly.io/prometheus/<org>/api/v1/query
  → fly_instance_cpu, fly_instance_memory_*, fly_instance_up
  → fly_edge_http_response_time, fly_app_concurrency

Resource attributes to check in sigiro spans:
  FLY_APP_NAME, FLY_MACHINE_ID, FLY_REGION, FLY_ALLOC_ID,
  FLY_IMAGE_REF, FLY_VM_MEMORY_MB, FLY_PROCESS_GROUP

Correlate: machine exit event vs error logs in sigiro_logs.
Correlate: memory metric spike vs slow spans.
Correlate: scale-to-zero restart vs cold start latency in spans.

### Railway

Data to fetch (via Railway GraphQL API, needs RAILWAY_TOKEN):
- Deployments: query { deployments(projectId: "<id>") { ... } }
  → deployment status, commit SHA, timestamps
- Service metrics: query { metrics(serviceId: "<id>") { ... } }
  → CPU, memory, network usage
- Logs: query { deploymentLogs(deploymentId: "<id>") { ... } }
  → build + runtime logs (Railway's own log stream)

Resource attributes to check in sigiro spans:
  RAILWAY_SERVICE_NAME, RAILWAY_ENVIRONMENT, RAILWAY_DEPLOYMENT_ID

Correlate: deployment timestamp vs error spike in sigiro_spans.

### GitHub Actions (CI/CD)

Data to fetch (via GitHub REST API, needs GITHUB_TOKEN):
- Workflow runs: GET /repos/<owner>/<repo>/actions/runs?per_page=10
  → run times, status, triggering commit SHA
- Failed jobs: GET /repos/<owner>/<repo>/actions/runs/<id>/jobs
  → step-level failure details

Correlate: merge/deploy workflow completion → deployment → error spike.
Use commit SHA to link: GitHub run → Vercel/Railway/Fly deployment → sigiro spans.

### GenAI SDK telemetry

If the app uses OpenAI, Anthropic, or other LLM APIs with OTel instrumentation
(e.g., opentelemetry-instrumentation-openai), these span attributes are already
in sigiro_spans:

  gen_ai.system          → "openai", "anthropic", etc.
  gen_ai.request.model   → "gpt-4", "claude-3-opus", etc.
  gen_ai.usage.input_tokens
  gen_ai.usage.output_tokens
  gen_ai.response.finish_reason

Useful queries:
  -- Cost by model (approximate)
  SELECT json_extract_string(span_attributes, '$.gen_ai.request.model') AS model,
         SUM(CAST(json_extract(span_attributes, '$.gen_ai.usage.input_tokens') AS BIGINT)) AS input_tokens,
         SUM(CAST(json_extract(span_attributes, '$.gen_ai.usage.output_tokens') AS BIGINT)) AS output_tokens
  FROM sigiro_spans
  WHERE json_extract_string(span_attributes, '$.gen_ai.system') IS NOT NULL
  GROUP BY model

  -- Slowest LLM calls
  SELECT span_name, duration/1000000 AS ms,
         json_extract_string(span_attributes, '$.gen_ai.request.model') AS model
  FROM sigiro_spans
  WHERE json_extract_string(span_attributes, '$.gen_ai.system') IS NOT NULL
  ORDER BY duration DESC
  LIMIT 20

## Gotchas

1. DuckDB file lock: only one process can open the DB for writing. Use HTTP API if server is running.
2. duration in sigiro_spans is nanoseconds, not milliseconds.
3. timestamp is a TIMESTAMP type (microsecond precision in DuckDB).
4. Linked trace queries (WHERE trace_id IN (...)) scan the full spans table. Cap trace_ids.
5. Always include service_name in WHERE for efficient filtering.
6. No profiles table — profiles are not supported in the current schema.
