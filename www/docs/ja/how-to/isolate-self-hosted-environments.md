開発・ステージング・本番を分離する必要がある場合は、**環境ごとにセルフホストの Sigiro インスタンスとデータディレクトリを 1 つずつ**用意します。OTLP とクエリのリスナー、ネットワーク境界の認証情報、ストレージとバックアップへのアクセス、保持期間も環境ごとに分けます。各環境のエクスポーターは対応する OTLP エンドポイントにのみ送信してください。ポートだけ分けても、データディレクトリやストレージバックエンドを共有すれば分離にはなりません。

ローカルバイナリでは、`sigiro serve` プロセスごとに別のディレクトリと 3 つの異なるリスナーポートを指定します。以下は開発専用ホストの例です。

```bash
SIGIRO_RETENTION_DAYS=2 sigiro serve \
  --data-dir /srv/sigiro/dev \
  --http-port 19999 --otlp-http-port 14318 --otlp-grpc-port 14317
```

ステージングと本番は**別プロセス**で、独立したパスと重複しないポートを使い、できれば別ホストまたは別ネットワークセグメントに配置します。この例は TLS も認証も設定しません。信頼できないネットワークにリスナーを公開しないでください。本番テレメトリー、バックアップ、ストレージ認証情報は本番のセキュリティ境界内に保ちます。保持期間は環境ごとに `SIGIRO_RETENTION_DAYS` で設定します。ディレクトリの削除は保持ポリシーの代わりにはなりません。コンテナのボリュームと localhost 限定のポートマッピングは[セルフホストのクイックスタート](/docs/tutorials/quickstart)、設定項目は[CLI リファレンス](/docs/reference/cli)を参照してください。

## 共有インスタンスでは分離できないもの

Open モードでは Sigiro は認証なしでリクエストを受け付け、合成された `default` テナントに割り当てます。`default` は**環境の境界ではありません**。開発と本番のリクエストを同じ Open モードのインスタンスに送ると、テナントとクエリの対象を共有します。本番と信頼度の低いトラフィックを共有の Open エンドポイントに送らないでください。このガイドは、未検証の認証済みテナント間の動作について保証しません。

`deployment.environment` は OpenTelemetry の**リソース属性**であり、Sigiro のプロジェクト ID や認可規則ではありません。意図的に共有したインスタンスではラベルを付けてクエリを絞り込めますが、ラベルの欠落、タイプミス、送信者が自由に指定できる値によって、データが混在したり漏れたりします。組み込みの診断などのクエリには、この SQL フィルターは自動適用されません。各スパンのリソースに `deployment.environment=staging` を設定した後、このリテラル SQL をインスタンスの `/v1/query` に送信できます。

```sql
SELECT service_name, count(*) AS span_count
FROM sigiro_spans
WHERE timestamp >= TIMESTAMP '2026-09-23 00:00:00'
  AND timestamp < TIMESTAMP '2026-09-24 00:00:00'
  AND (resource_attributes::JSON->>'deployment.environment') = 'staging'
GROUP BY service_name
ORDER BY span_count DESC;
```

2 つの日時を対象の有限な半開区間に変更してください。この値は `sigiro_spans.resource_attributes` に保存された JSON 文字列から読み取ります。独立した列ではありません。このフィルターは**クエリ上の規約**にすぎず、アクセス制御やストレージ分離、別インスタンスの代替にはなりません。

## トレードオフ

ストレージとネットワークのアクセスも分離すれば、別インスタンスの Open モードのクエリエンドポイントから他環境のデータを読み取ることはできません。ただし、開発・ステージング・本番をまたぐ単一のローカルクエリは利用できません。比較する場合は各エンドポイントを別々に照会し、認可された外部ワークフローで結果を結合してください。そのワークフローへのアクセス権を環境ごとに明示的に付与します。共有インスタンスでは環境横断の SQL が容易になる一方、分離を失い、フィルタリングが運用者の責任になります。リモートの OTLP またはクエリへのアクセスは TLS とアクセス制御付きの入口、または信頼できるプライベートネットワークで保護してください。公開された平文接続で認証情報やテレメトリーを送らないでください。入口、エクスポーター、ストレージの認証情報を環境ごとに分けて管理・ローテーションしてください。
