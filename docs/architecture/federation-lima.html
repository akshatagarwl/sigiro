Test Flow

1 Catalog — PostgreSQL container started on host as shared catalog (hard requirement) docker run postgres:17
2 Build — Docker cross-compiles Linux ARM64 sigiro binary docker build
3 Install — spice install downloads spiced runtime on central VM curl | bash
4 Copy — Binary copied to both VMs via limactl copy limactl copy
5 Start Central — sigiro serve with SIGIRO_CENTRAL=true + SIGIRO_CATALOG_URL HTTP :10000
6 Start Worker — sigiro serve with SIGIRO_CENTRAL_URL + SIGIRO_CATALOG_URL HTTP :10001
7 Register — Worker POSTs its metadata to central's /v1/federation/workers POST /v1/federation/workers
8 Spicepod — Central regenerates spicepod.yaml with worker dataset regenerate_spicepod()
9 Ingest — Host sends OTLP trace to worker via forwarded port 10102 POST /v1/traces
10 Query — Host queries worker via forwarded port 10001 POST /v1/query

Validation Checklist

Central health endpoint responds ✓ PASS Worker health endpoint responds ✓ PASS Worker appears in /v1/federation/workers ✓ PASS Worker endpoint matches expected URL ✓ PASS spicepod.yaml contains worker dataset ✓ PASS OTLP trace accepted by worker ✓ PASS Trace query returns data ✓ PASS spiced process running on central ⚠ WARN*
Hard Requirement: Shared Catalog
Federation mode (SIGIRO_CENTRAL=true or SIGIRO_CENTRAL_URL set) fail-fasts if SIGIRO_CATALOG_URL is missing. Local SQLite lives on each VM's isolated filesystem — central cannot read worker catalogs. PostgreSQL (or another network-accessible catalog) is mandatory.
* Why the spiced warning?
spiced may exit because the worker's catalog.sqlite path in spicepod.yaml still points to a local file. Even with shared PostgreSQL catalog metadata, the ducklake connector needs access to the actual catalog file. Full cross-VM data federation requires either S3-backed data or mounting shared storage. The test validates the control plane (registration + spicepod generation) which is architecturally complete.
